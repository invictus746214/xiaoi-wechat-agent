# r10 响应与可靠性优化

用户已批准六项：启动提速、语音分段测量与优化、撤销过时回复、历史表情定位收藏、跟进改期、明确不回复原因。

## 方案和验收

1. 旧记忆兼容迁移按账号持久化版本标记；没有待迁移旧数据时不碰界面。迁移失败/中断不写完成标记，成功后重启不再全量扫描，不丢既有别名。
2. 语音先分段计时，再优化测得的瓶颈。保留本地处理、单进程、384 MiB 常驻内存看门狗、12 秒 CPU、15 秒识别子进程时限，以及源消息验证。
3. 新补充、改题或明确已有他人回答时，不发送尚未提交的旧草稿。已开始或未知发送状态保留回执，不自动重放；同一人未处理的新信息不丢失。
4. 历史表情按账号、会话、原消息和原图校验，在有界空闲任务中扫描和恢复进度。只点已识别的收藏控件，模糊匹配不操作，未知结果不重试。
5. 改期/取消/完成信息只作用于本人原私聊的已验证跟进。新时间需明确同意；多个候选或时间不明则澄清，不覆盖发送中/未确认记录。
6. 诊断区分离线/读取异常、识别超时、生成、主动沉默、策略/额度和送达未确认。普通查询限制当前会话；主人可查看脱敏运行状态，不泄露其他聊天内容。

沿用 Python、SQLite 和唯一 GUI 执行器，不扩大管理或代发权限。每日朋友圈点赞与评论额度各 20，部署保留源码/配置备份；回滚不回退最新回执库。

## 使用与边界

- 发“消息处理状态”“为什么没回复”可查当前会话处理原因、语音阶段耗时和最近一次运行检查。离线时无法通过微信实时回答查询，恢复后可查；超过五分钟的检查明确标为过期。
- 私聊新输入持久入队后，未提交的旧模型草稿撤销，原发言以去重记录留在上下文。指令结果、已创建发送计划和未知送达记录不撤销。严格 @ 群聊只在替代消息自身也 @ 或引用小i 时替换，避免丢掉原消息的回复许可；普通补充保留原回复。
- 未被 @ 的主动群回复遇到新讨论会让位，不臆测其他人的消息已经完整回答了原问题。
- 历史收藏按原消息定位，保存扫描锚点与偏移；没有可读滚动条且不能核对唯一最新文字时停止。单来源最多核验 2000 条；约 4.5 秒是定位后的扫描预算，不包含既有有界解码和会话选择。两次真机试跑总耗时约 13.8 / 23.9 秒，均保存了进度且未提交收藏。原图保存、素材可复用、原生收藏是三个不同状态。
- 跟进改期例：“我面试改期到后天下午3点”，再确认“同意调整跟进”；多个候选需指定 ID。取消或完成会停止原跟进；发送中和送达未知的记录仍不重发。
- 首次旧记忆扫描完成才写账号/版本标记。迁移失败或中断不写；后续另行导入旧格式记忆时需提升 `startup_memory.MIGRATION_VERSION`。

## 验证

语音两条同来源本机 A/B：12.50→11.68 秒、13.77→13.29 秒，平均约改善 5%；主要耗时仍在识别计算，没有放宽原资源和超时限制。音频与转写正文均留在服务器。

## 回滚

停止唯一服务后，从本次备份恢复改动源码和配置，移除本次新增的 `startup_memory.py`，再启动。不要覆盖实时状态数据库。

**恢复 r9 前必须检查 `followup_changes` 中是否仍有 `state='select'` 的歧义跟进。若有，先把配置中的 `tasks.enabled` 和 `followups.enabled` 都设为 false，再启动旧版。** 旧版不认识这些暂停记录，只关闭 followups 不能阻止 Tasks 投递。待人工处理这些候选后再恢复任务投递。
